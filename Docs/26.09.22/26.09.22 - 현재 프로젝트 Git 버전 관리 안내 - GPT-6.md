## 확인한 현재 상태

- 저장소: `D:\_Projects\FPS_Dell2g`, 현재 브랜치 `master`.
- 기존 커밋 2개: 최신 `682ce97` (`26.09.09`), 이전 `ce0cebc` (`기본 FPS 메쉬, 컨트롤러 설정`). 새로 `git init`을 할 필요가 없다.
- 추적 중인 파일 5개에 미커밋 변경이 있고, 제외 규칙을 통과하는 미추적 파일은 123개다. 배드민턴 코드, 테스트, 스크립트, 실행 런처 등이 포함된다. Git 저장소가 있다는 것만으로 이 변경들이 버전으로 저장되지는 않는다.

- Git LFS 3.7.0은 설치되어 있으나 루트 `.gitattributes`는 없다. 프로젝트의 LFS 관리 규칙 설정은 별도로 필요하다.
- Git 명령에서 사용자 전역 ignore 파일 읽기 권한 경고가 발생했다. 저장소 상태 조회는 가능했으나 전역 제외 규칙의 내용은 확인하지 못했다.

## 권장 운영 방식

Git의 커밋은 이름을 붙인 저장 지점이다. 브랜치는 실험할 작업 흐름을 분리하며, 원격 저장소는 다른 장소에 이력을 보관하고 공유하는 데 사용한다. 파일 수정 후 저장만 해서는 새 커밋이 생기지 않는다. 선택한 변경을 `git add`로 준비하고 `git commit`으로 기록한다. [Git 공식 문서](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)

이 프로젝트에는 다음 순서를 권장한다.

1. 현재 작업을 기준 버전으로 보존한다. 신규·변경 파일을 검토하고, 코드·설정·필요한 스크립트를 포함하는 기준 커밋을 만든다. 아직 검증하지 않은 현재 상태를 검증 완료 버전이라고 이름 붙이지 않는다.
2. 새 기능마다 `codex/기능명` 브랜치를 만든다. 예: `codex/smash-adjustment`.
3. 기능 단위로 변경·검증·커밋한다. 예: `스매시 판정 범위 조정`, `재경기 점수 초기화 오류 수정`. 빌드와 관련 동작 검증 결과를 문서에 남긴다.
4. 검증한 작업을 `master`에 합친다. 현재 브랜치명은 그대로 사용해도 된다.
5. 검증된 중요 버전에 태그를 붙인다. 예: `v0.1.0-local-mvp`. EOS 외부망 검증이 남아 있으면 배포 완료로 표시하지 않는다.
6. GitHub 등을 사용할 경우 비공개 원격 저장소를 만들고 연결한 뒤 push한다. 로컬 커밋만으로는 PC 장애에 대비한 외부 백업이 되지 않는다.

## 무엇을 저장할지

| 대상 | 권장 처리 |
| --- | --- |
| `Source/`, `Config/`, `.uproject` | Git으로 관리. 설정 파일의 개인 경로·비밀 값은 제외 |
| 필요한 `Scripts/`, 실행 `.cmd`, 프로젝트 플러그인 소스·설명 파일 | 검토 후 Git으로 관리 |
| `Build/` | 필요한 빌드 리소스인지 확인 후 선별 |
| `Content/`의 맵·블루프린트·데이터·에셋 | 같은 게임 상태 복원이 목적이면 함께 관리. 필요한 참조 에셋도 포함 |
| `Docs/`의 작업 문서, `AGENTS.md` | 문서와 지침도 이력 관리하도록 제외 규칙 조정 권장 |
| `Docs/_녹화파일/` | 일반 코드 저장소에서 제외하고 영상은 별도 보관 권장 |
| `Binaries/`, `Intermediate/`, `DerivedDataCache/`, `Saved/`, `.vs/` | 생성물이므로 제외 유지 |
| `LocalSecrets/` | 제외 유지. 원격에 업로드하지 않음 |

코드만 관리하려면 현재 Content 제외 정책을 유지할 수 있다. 다만 과거 커밋으로 코드를 되돌려도 맵·블루프린트 상태는 되돌아오지 않는다. 게임 전체를 복원하려면 Content 관리가 필요하다.

Content를 포함하기로 하면 `.gitignore`의 `Content` 제외와 개별 에셋 제외 규칙을 검토한다. 문서를 포함하려면 `Docs`, `*.md` 제외를 조정하고, 광범위한 `*.txt` 제외도 필요한 파일을 숨기지 않는지 검토한다. 기존의 개별 제외 규칙을 무작정 전부 제거하지 않는다.

에셋을 처음 추가하기 전에 다음과 같이 LFS를 설정할 수 있다. 이 명령은 안내용이며 이번 작업에서 실행하지 않았다.

```powershell
git lfs install
git lfs track "*.uasset"
git lfs track "*.umap"
git add .gitattributes
```

`.gitattributes`도 커밋해야 다른 환경에서 같은 규칙이 적용된다. 이미 일반 Git에 저장된 파일의 과거 이력은 `git lfs track`만으로 변환되지 않는다. [GitHub 공식 LFS 설정 문서](https://docs.github.com/en/repositories/working-with-files/managing-large-files/configuring-git-large-file-storage)

## 명령어 예시

아래는 현재 기준 커밋을 만든 후 새 기능을 작업하는 예시다. 기준 커밋에 포함할 전체 파일은 먼저 검토해야 하므로 무조건 `git add .`를 실행하지 않는다.

```powershell
Set-Location 'D:\_Projects\FPS_Dell2g'
git status
git switch -c codex/smash-adjustment

# 기능 수정과 필요한 빌드·동작 검증 후 실행
git diff
git add Source/FPS_Dell2g/Badminton
git diff --cached --stat
git diff --cached
git commit -m "스매시 판정 범위 조정"

# 해당 기능의 필요한 파일이 모두 커밋되어 있고 검증이 끝난 경우
git switch master
git merge codex/smash-adjustment
git log --oneline -10
```

위 `git add`는 예시 폴더만 포함한다. 실제로 수정한 설정·테스트·문서도 해당 기능에 필요한 범위로 함께 준비해야 한다. 새 파일의 내용은 `git diff`만으로 보이지 않으므로 별도로 읽거나 staging 후 `git diff --cached`에서 검토한다.

원격 백업을 원한다면 GitHub에서 README 등으로 초기화하지 않은 빈 비공개 저장소를 만든 후 아래 명령을 사용할 수 있다. 주소는 실제 저장소 주소로 대체한다. 이번 작업에서는 생성·연결·push하지 않았다.

```powershell
git remote add origin 'https://github.com/계정명/FPS_Dell2g.git'
git push -u origin master
```
