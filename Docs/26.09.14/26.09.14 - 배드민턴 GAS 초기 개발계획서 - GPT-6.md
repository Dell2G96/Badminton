# 배드민턴 멀티플레이 게임 초기 개발계획서

작성일: 2026-09-14 · 버전: 0.3 · 작성 모델: GPT-6 · 가칭: Shuttle Arena

**사용자 확정 사항 (2026-09-14)**

첫 배포는 EOS 기반 인터넷 방 생성·검색·참가를 포함한다. LAN/직접 IP는 초기 검증 단계이며 최종 배포 완료 조건이 아니다. EOS 제품·Sandbox·Deployment가 아직 없어 별도 생성·연결 안내를 작성했다. OBSRecording은 사용자 선택에 따라 임시 비활성화한다. 아래 기간은 EOS 제품 준비와 외부망 검증을 반영하여 재산정한다.

**기획 방향**

Unreal Engine 5와 Gameplay Ability System(GAS)을 활용하여, 타격 타이밍과 상대 코트의 빈 공간 공략이 중심인 1대1 배드민턴 멀티플레이 게임을 제작한다. 첫 번째 목표는 두 플레이어가 접속하여 서브부터 랠리, 득점, 경기 종료, 재경기까지 진행할 수 있는 플레이 가능한 빌드다.

실제 배드민턴의 샷 선택과 위치 싸움을 살리되, 조작과 판정에는 적절한 보정을 적용하는 아케이드 스포츠를 지향한다. 아래 인원·기간·플랫폼은 확정 요구사항이 아닌 초기 산정용 가정이다.

| 항목 | 초기 가정 |
|---|---|
| 개발 인원 | 개발자 1명, 캐릭터·애니메이션은 기존 에셋 활용 |
| 플랫폼 | Windows PC, 키보드·마우스 우선 |
| 엔진 | 현재 프로젝트의 UE 5.7을 기준으로 시작하고 플러그인·에셋 호환성 검증 |
| 구현 | C++ 기반 핵심 로직 + Blueprint 기반 연출·UI·데이터 조정 |
| 게임 모드 | 1대1 단식, 코트 1개, 동일 능력치 캐릭터 |
| 카메라 | 자신의 코트 뒤에서 양쪽 코트를 보는 높은 3인칭 카메라 |
| 초기 네트워크 | Listen Server, LAN 또는 직접 IP 접속 |
| 목표 기간 | UE C++ 기초 경험 기준 10주 내외, GAS 학습이 필요하면 2~4주 추가 |

**1. 플레이 경험과 경기 흐름**

플레이어는 셔틀콕의 위치와 상대의 움직임을 보고 이동한 뒤, 타이밍에 맞춰 샷 종류와 방향을 선택한다. 클리어로 시간을 벌고, 드롭으로 전진을 유도하며, 높은 셔틀콕을 스매시로 마무리하는 선택 구조를 만든다.

경기 흐름은 `접속 → 대기 및 준비 → 서브 준비 → 랠리 → 득점 판정 → 다음 서브 → 경기 결과 → 재경기`로 구성한다.

초기 조작안:

| 입력 | 행동 | 설계 의도 |
|---|---|---|
| WASD | 코트 내 이동 | 위치 선정과 타격 준비 |
| 마우스 이동 | 상대 코트 목표 지점 조정 | 이동 방향과 샷 방향 분리 |
| 좌클릭 | 기본 리턴/클리어, 서브 상황에서는 서브 | 가장 먼저 완성할 기본 조작 |
| 우클릭 | 드롭 | 네트 앞 공간 공략 |
| Space | 스매시 | 높은 타점에서 공격, 스태미나 소모 |
| Shift + 이동 방향 | 짧은 대시 | 긴급 수비, 연속 사용 제한 |

입력은 설정 가능한 액션으로 정의한다. 기본 타격은 스태미나가 부족해도 가능하게 하여 경기 진행이 막히지 않도록 한다. 스매시와 대시에만 초기 비용을 적용한다. 점프 스매시, 다이빙, 차지 조작은 기본 랠리의 재미를 확인한 뒤 검토한다.

타격 성공 여부는 서버가 타격 가능 거리·높이·방향·시간 구간을 확인하여 결정한다. 성공한 샷의 품질은 타이밍, 타점, 선택한 샷 종류에 따라 조정한다. 정밀한 라켓 메시 충돌만으로 판정하기보다 전용 타격 영역과 유효 시간 구간을 사용하여 조작 안정성을 확보한다.

**2. 최소 기능 제품(MVP) 범위**

| 구분 | 포함 기능 | 완료 기준 |
|---|---|---|
| 접속 | 호스트 생성, 클라이언트 접속, 준비 상태 | 별도 프로세스 2개에서 입장 및 경기 시작 |
| 이동 | 기본 이동, 코트 경계, 대시 | 상대 움직임이 복제되고 코트 이탈 방지 |
| 타격 | 서브, 기본 리턴/클리어, 드롭, 스매시 | 각 샷이 서로 다른 궤적과 사용 조건을 가짐 |
| 셔틀콕 | 비행, 네트 충돌, 바닥 및 아웃 판정 | 모든 플레이어에게 동일한 랠리 결과 전달 |
| 경기 | 득점, 서브권, 경기 종료, 재경기 | 한 경기를 끝내고 새 경기를 시작 가능 |
| GAS | 능력, 스태미나, 비용·회복, 행동 제한, 연출 | 중복 발동과 비용 중복 차감 방지 |
| UI | 점수, 스태미나, 서브 안내, 결과, 접속 오류 | 경기 상태와 실패 이유 확인 가능 |
| 테스트 | 지연·손실 조건, 호스트/참가자 비교 | 네트워크 조건별 결과와 남은 문제 기록 |

첫 배포 추가 범위: EOS 로그인, 2인 방 생성·검색·참가, 접속 실패·종료 처리, 서로 다른 인터넷 연결에서의 P2P 검증.

후속 범위: 2대2 복식, AI 상대, Steam 추가 연동, 전용 서버 배포, 랭크 매칭, 관전, 리플레이, 성장 시스템, 장비 능력치, 꾸미기, 게임패드 지원.

초기 직접 IP 접속은 인터넷 환경의 방 검색이나 NAT 통과를 보장하지 않는다. 사용자가 인터넷 플레이를 첫 공개 목표로 확정했으므로 EOS 연동과 실제 외부망 테스트를 일정에 추가한다.

**3. 경기 규칙 초안**

첫 빌드는 개발과 반복 테스트에 맞춘 자체 간소화 규칙을 사용한다. 공식 대회 규칙을 완전히 구현하는 범위는 아니다.

- 단식, 랠리마다 1점, 11점 선취 단판, 듀스 없음.
- 첫 서브는 서버에서 무작위 결정하고 이후 랠리 승자가 서브한다.
- 서브는 지정된 위치에서 대각선 서비스 구역으로 보낸다. 점수의 홀짝에 따라 서브 위치를 전환한다.
- 상대 코트 안에 셔틀콕을 떨어뜨리면 득점한다. 경계선은 인으로 처리한다.
- 코트 밖 착지, 자신의 코트 착지, 잘못된 서비스 구역 착지, 연속 두 번 타격은 실점 처리한다.
- 네트에 닿았다는 이유만으로 즉시 실점시키지 않는다. 통과·낙하 결과에 따라 랠리를 지속하거나 종료한다.
- 네트에 걸려 진행이 멈춘 경우와 장시간 비행하는 비정상 상황은 서버의 예외 처리로 정리한다.
- 득점은 랠리당 한 번만 확정하고, 확정 후 들어온 늦은 타격 요청은 무시한다.

점수 한도와 규칙은 `MatchRuleData`로 분리한다. 코트·서비스 구역·라인 허용 오차도 데이터로 관리하고, 네트·바닥·라인 판정은 서버에서 일관되게 처리한다.

**4. GAS 적용 설계**

GAS는 캐릭터의 행동, 속성, 비용, 상태와 연출을 관리하는 데 사용한다. GAS가 제공하는 Ability, Attribute, Effect, Task 구조를 배드민턴 행동에 대응시킨다. [Epic Games: Gameplay Ability System](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-ability-system-for-unreal-engine)

아래 이름과 배치는 이 프로젝트를 위한 설계안이다.

| GAS 구성 | 초기 설계 | 책임 |
|---|---|---|
| AbilitySystemComponent | PlayerState에 소유, Character를 Avatar로 연결 | 능력 보유, 속성 및 상태 관리 |
| AttributeSet | Stamina, MaxStamina | 행동 자원과 UI 연결 |
| GameplayAbility | GA_Serve, GA_Clear, GA_Drop, GA_Smash, GA_Dash | 발동 조건, 동작 진행, 종료 및 취소 |
| GameplayEffect | GE_SmashCost, GE_DashCost, GE_StaminaRegen, GE_DashCooldown | 비용, 회복, 재사용 제한 |
| GameplayTag | State.Serving, State.Swinging, State.Recovering | 동시 행동 제한과 상태 표현 |
| GameplayCue | GameplayCue.Shot.Hit, GameplayCue.Shot.Smash | 타격음, 파티클, 카메라 반응 |
| AbilityTask | 몽타주 재생·입력·이벤트 대기 | 준비→타격→후딜레이 흐름 조율 |

설계 원칙:

- 기본 이동은 CharacterMovementComponent를 사용한다. 모든 이동 입력을 Ability로 만들 필요는 없다.
- 대시는 이동 예측과 호환되는 방식으로 구현한다. 로컬 위치를 직접 순간 변경하는 방식은 피한다.
- 샷별 궤적, 발사각 범위, 목표 지점 보정, 타격 구간은 `ShotDataAsset`로 관리한다.
- 초기에는 타격 능력을 공통 기반 클래스와 샷 데이터로 구성하여 검증 로직의 중복을 줄인다.
- 타격 후딜레이에는 다른 타격 발동을 차단한다. 애니메이션 취소·경기 종료·접속 해제 시 태그와 대기 작업을 정리한다.
- 능력 부여는 서버에서 수행하고, 서버 소유 및 클라이언트 PlayerState 복제 시점에 ASC의 Owner/Avatar 연결을 초기화한다. 재경기나 Pawn 교체 시 중복 부여를 방지한다.
- 경기 점수와 랠리 상태는 GameState에서 관리한다. GAS 태그가 경기 상태의 별도 원본이 되지 않도록 한다.

**5. 서버 권한과 셔틀콕 동기화**

이 프로젝트에서 가장 먼저 검증할 기술 문제는 빠른 셔틀콕을 지연이 있는 환경에서 자연스럽게 주고받는 것이다. Epic의 문서에서도 빠른 물체와 높은 지연은 물리 상호작용 복제를 어렵게 만드는 요인으로 설명한다. 이에 따라 초기에는 조정 가능한 전용 셔틀콕 시뮬레이션을 제안한다. [Epic Games: Networked Physics Overview](https://dev.epicgames.com/documentation/unreal-engine/networked-physics-overview)

| 항목 | 최종 결정 | 클라이언트 역할 |
|---|---|---|
| 캐릭터 이동 | 서버 검증 및 보정 | 로컬 입력 예측 |
| 타격 능력 | 서버 발동 조건 검증 | 입력 직후 스윙과 일부 연출 표시 |
| 타격 성공 | 서버의 거리·상태·시간 검증 | 샷 종류, 목표 방향, 요청 식별자 전송 |
| 셔틀콕 궤적·충돌 | 서버 시뮬레이션 | 수신 상태 보간 및 제한적 외삽 |
| 스태미나 | 서버 확정 | 가능한 범위에서 예측 표시 후 보정 |
| 득점·승패·서브권 | 서버 확정 | 복제된 경기 상태 표시 |

GAS의 Local Predicted 정책은 입력 직후 능력을 시작하고 서버 결과로 보정하는 데 활용할 수 있다. 셔틀콕의 궤적 예측, 타격 시점의 지연 보상, 득점 판정은 별도로 구현해야 한다. [Epic Games: Gameplay Ability](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine)

셔틀콕 구현안:

1. 서버에서 위치·속도·중력·속도에 따른 항력을 계산한다. 단순 포물선으로 시작하되 클리어·드롭·스매시의 차이를 데이터로 조정한다.
2. 고정 간격 시뮬레이션 또는 제한된 서브스텝과 이동 경로 Sweep 판정을 사용하여 빠른 셔틀콕이 네트와 바닥을 통과하는 문제를 줄인다.
3. 위치, 속도, 서버 시간, 랠리 ID, 샷 시퀀스를 주기적으로 복제한다. 타격으로 궤적이 바뀌면 새 상태를 즉시 전송한다.
4. 클라이언트는 서버 시간을 기준으로 화면상 궤적을 보간한다. 단절 시 외삽 시간을 제한하고 오래된 시퀀스는 적용하지 않는다.
5. 화면상 셔틀콕과 서버 판정 시점의 차이를 계측한다. 필요하면 제한된 과거 상태 기록을 사용한 타격 검증을 추가한다.
6. 과거 시점 타격을 승인할 경우 그 시점부터 현재까지 궤적을 다시 계산하고, 이미 확정한 랠리와 충돌하는 요청은 거절한다. 입력 시각은 허용 범위로 제한하고 클라이언트가 보낸 위치나 성공 여부를 신뢰하지 않는다.

타격 요청 처리 흐름:

`입력 → 로컬 Ability/스윙 시작 → 서버가 상태·비용·타격 구간 검증 → 서버가 셔틀콕 접촉 확인 → 새 샷 상태 확정 → 클라이언트 궤적 및 연출 보정`

비용 정책은 능력 발동 승인 시 1회 차감으로 통일한다. 헛스윙은 비용을 유지하고, 발동 자체가 거절되면 예측 비용을 복구한다. 타격 요청 중복 방지와 한 스윙당 한 번의 타격 소비 처리를 별도로 둔다.

서버 판정은 렌더링 여부나 클라이언트 애니메이션 Notify만으로 진행하지 않는다. 서버 시간과 샷 데이터의 타격 구간을 기준으로 검사하여 전용 서버에서도 같은 로직을 사용할 수 있게 한다.

**7. 개발 일정과 단계별 완료 기준**

일정은 추정치이며, 네트워크 타격 검증 결과에 따라 재산정한다. 초기부터 멀티플레이를 전제로 구현하는 방향은 Epic의 네트워킹 가이드와도 일치한다. [Epic Games: Networking Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)

| 기간 | 구현 내용 | 완료 기준 |
|---|---|---|
| 1주차 | UE C++ 프로젝트, 입력, 코트, 카메라, 2인 접속 | 두 플레이어가 같은 코트에서 이동 |
| 2주차 | ASC·속성 초기화, 기본 타격 Ability, 단순 셔틀 비행 | 서버 승인 타격으로 기본 리턴 가능 |
| 3주차 | 셔틀 복제, Sweep 충돌, 샷 시퀀스, 지연 테스트 | RTT 100ms 조건에서 기본 랠리를 반복하고 오류 기록 |
| 4주차 | 타격 검증 개선, 보간 조정, 필요 시 제한적 지연 보상 | 기본 랠리에서 중복 타격·중복 득점 방지 |
| 5주차 | 드롭·스매시·대시, 비용·회복·상태 제한 | 샷 선택과 스태미나 사용에 의미 있는 차이 |
| 6주차 | 서브·득점·아웃·경기 결과·재경기 | 간소화 규칙으로 한 경기 전체 플레이 |
| 7주차 | 애니메이션, 사운드, 이펙트, 경기 UI | 타격 성공·실패와 다음 행동을 화면에서 이해 가능 |
| 8주차 및 추가 일정 | EOS 로그인·방 생성·검색·참가, 별도 PC·외부망 테스트, 접속 해제, 지연·손실 대응 | EOS로 접속부터 결과까지 패키징 빌드 검증; 제품 준비·연동 난이도에 따라 일정 재산정 |
| 9주차 | 플레이테스트, 판정·카메라·샷 밸런스 개선 | 주요 플레이 방해 문제 수정 |
| 10주차 | 버그 수정 여유, 실행 안내, 구조도, 시연 영상 | 재현 가능한 실행 빌드와 문서 전달 |

3~4주차 검증에서 랠리 품질이 목표에 미치지 못하면 샷과 연출 추가를 미루고 동기화를 먼저 해결한다. 일정이 부족할 때 축소 순서는 대시 → 드롭 → 고급 연출이며, 기본 타격·서브·판정·한 경기 흐름은 유지한다.

**8. 검증 계획**

아래 수치는 초기 합격 목표이며 실제 달성 결과를 의미하지 않는다. 기준 PC 사양은 첫 프로파일링 시 문서화한다.

| 검증 항목 | 초기 목표 |
|---|---|
| 기본 경기 | 패키징된 호스트·클라이언트에서 10경기 연속 종료 및 재경기 가능 |
| 점수 일관성 | 각 랠리 종료 후 두 화면의 점수·서브권 일치, 중복 득점 0건 |
| 네트워크 | RTT 0/50/100/150ms, 패킷 손실 0/1/3% 조합 테스트 |
| 핵심 플레이 | RTT 100ms·손실 1%에서 숙련 테스트 입력으로 10회 이상 왕복 랠리 가능 |
| 예측 및 보정 | 입력→스윙 시간, 타격 거절률, 셔틀 위치 오차와 보정량의 중앙값·상위 95% 기록 |
| 예외 처리 | 연속 입력, 늦은 요청, 랠리 종료 직전 타격, 스태미나 부족, 네트 걸림 확인 |
| 접속 해제 | 클라이언트 이탈 시 상대에게 안내, 호스트 종료 시 참가자를 접속 화면으로 복귀 |
| 성능 | 합의한 기준 PC에서 1080p 60fps 목표, 서버 시뮬레이션 및 복제 비용 측정 |

RTT 표기는 왕복 지연 기준이다. 네트워크 에뮬레이션 설정이 편도인지 확인하여 실제 측정값을 함께 기록한다. 150ms·손실 3%는 열악한 환경에서 게임이 멈추거나 상태가 엇갈리는지 확인하는 스트레스 조건으로 사용한다.

자동 검증은 점수 전환, 서비스 구역 판정, 오래된 요청 거절, 중복 타격 처리처럼 결과가 명확한 로직에 집중한다. 손맛과 시각적 보정 품질은 실제 두 플레이어의 플레이테스트로 확인한다.

**10. 산출물과 착수 작업**

최종 산출물은 Windows 실행 빌드, Unreal 프로젝트 소스, 호스트·참가자 실행 안내, GAS 및 네트워크 구조 문서, 네트워크 테스트 결과, 1~2분 경기 시연 영상으로 구성한다.

착수 순서:

1. 엔진 버전과 에셋 호환성을 정하고 C++ 프로젝트를 생성한다.
2. GameplayAbilities, GameplayTags, GameplayTasks와 Enhanced Input 사용 구성을 준비한다.
3. GameMode·GameState·PlayerState·Character·Controller 기본 클래스를 만든다.
4. 블록아웃 코트와 카메라를 만들고 두 클라이언트 이동을 확인한다.
5. ASC와 Stamina를 연결하고 GA_Clear 하나로 서버 승인 타격을 구현한다.
6. AShuttlecock과 단순 궤적을 추가하여 두 플레이어의 기본 랠리를 완성한다.
7. 지연을 적용해 판정과 표시 오차를 측정한 후 샷 종류와 경기 규칙을 확장한다.

개발 착수 전 우선 확정할 항목은 사용 엔진 버전, 실제 개발 가능 시간, 에셋 확보 방식, 최종 목표가 LAN 시연인지 인터넷 공개 플레이인지다. 응답이 없는 단계에서는 위 초기 가정을 기준으로 계획을 구체화한다.
