## 초기 조사 및 계측 설계

SendShot은 HandleGameplayEvent로 LocalPredicted 능력을 발동한다. 엔진은 예측 키를 포함한 ServerTryActivateAbilityWithEventData RPC를 보낸다. 입력→로컬 활성화→서버 활성화→접촉→종료를 기존 예측 키와 같은 PC QPC 로그로 연결한다. 이벤트 발동 수와 상태 태그·거리·높이·랠리·시퀀스를 함께 남겨 입력 부재, 로컬 발동 차단, 서버 도착 지연을 구분한다.

새 계측은 기존 BadmintonNetMetrics 선택 시만 활성화한다. 추가 RPC나 클라이언트 시각을 담은 판정 데이터는 만들지 않는다. 예측 키는 플레이어별·실행별로 구분하며 같은 PC의 같은 실행 로그만 시각 비교에 사용한다. 서버 접촉 허용 높이·거리와 자동 Aim 기대값을 변경하지 않는다.

PIE 직접 조작·사람의 플레이·별도 PC/LAN·MP4는 네이티브 앱 제어가 비활성화된 현재 환경에서 수행할 수 없어 별도 미완료로 남긴다.

## 구현 내용

- `BadmintonShotDiagnostics.h`와 Controller/기본 샷 능력에서 Input, Dispatch, Activate, Contact, End를 기록한다. qpc, 권한, 진영, 랠리, 시퀀스, 샷, GAS 예측 키, 결과, 단계, 셔틀 거리·높이와 상태 태그가 포함된다. 일반 실행과 Shipping의 계측은 꺼져 있다.
- `Measure-BadmintonShotFlow.ps1`이 입력→로컬 활성화, 로컬→서버 활성화, 서버 활성화→접촉의 구간 시간을 날짜별 Markdown으로 만든다. 로컬 입력은 SendShot 소프트웨어 진입 시각이며 물리 입력 장치 지연을 포함하지 않는다.
- 호스트/참가자의 같은 실행 GUID·Windows QPC·머신·표시 모델과 SameMachine 선언을 요구한다. 플레이어·샷·키별 일대일 매칭만 허용하고 중복 키·역전 시각·서버 활성화 부재를 분리한다. 재접속·키 재사용이 포함된 장시간 로그는 대상이 아니다.
- 각 프로세스 최초 TEST PASS/FAIL까지로 집계를 고정한다. End와 반복 입력 기록은 근거 로그에 보존하고 발동 0인 Dispatch 수를 표시한다. 정상 회복 태그 때문에 차단된 반복 입력을 모두 버그로 집계하지 않는다.
- `Test-BadmintonNetwork.ps1 -ShotFlow`가 NetMetrics+PositionTrace를 함께 켠다. 성공·실패 모두 finally에서 이번 검사의 프로세스를 정리한 후 흐름 보고서를 작성한다. 초기화 실패로 메타데이터가 없다면 보고서 경고를 별도로 남기고 원래 게임 검사 오류를 보존한다.
- `-TransportTrace`는 ShotFlow와 엔진 `net.Reliable.Debug 1`, LogNetTraffic Log, LogAbilitySystem Verbose를 선택한다. RPC 송신·재전송 로그의 후속 조사용이며 로그 비용이 크다.
- Aim 프로브에서 중간 득점을 즉시 `rally ended before ten alternating shots`와 점수·랠리·관측 샷 수로 설명하도록 바꿨다. 10회 교대 랠리 성공 조건은 그대로다. 예전의 뒤이은 새 서브 목표 차이 때문에 일반적인 `replicated aim/target`로 보이던 진단을 구체화한 것이다.

따라서 이 실행에서는 최초 입력이 없었던 것이 아니고, 로컬 GAS 진입이나 서버 TryShot 내부 대기보다 **로컬 활성화 이후 서버 활성화 이전의 약 290ms 구간**이 핵심이다. 반복 입력 중 다수가 State.Swinging으로 차단되는 것은 회복 시간 0.35초의 정상 동작이며, 이를 제거하면 중복 타격/비용 규칙을 깨뜨릴 수 있다.

NoServerActivation이라는 분석 상태만으로 요청 유실이라고 판단하지 않는다. 이번 key 2는 엔진 거절 로그가 있어 실제 서버 도착과 사전 거절을 확인했다. 해당 로그에는 거절 태그가 비어 있으므로 구체적인 CanActivate 조건은 당시 경기 단계와 코드에 근거한 해석이다.

### 원인 판단의 한계

로컬 엔진의 AbilitySystemComponent.h에서 ServerTryActivateAbilityWithEventData는 Reliable RPC다. AbilitySystemComponent_Abilities.cpp는 로컬 예측 키를 생성하고 해당 RPC를 보낸 뒤 로컬 능력을 실행한다. 서버는 CanActivate 검사를 통과한 후 능력 본문을 실행한다. DataChannel.cpp는 Reliable 순서 유지와 NAK/ACK timeout 재전송을 구현한다.

그러나 실패 당시 개별 패킷 ID·해당 RPC bunch의 재전송을 직접 연결한 자료는 없다. 290ms에는 전송·재전송·큐·엔진 프레임 처리 등이 포함된다. 추가 TransportTrace 실행에서는 제어 채널 재전송이 보였지만 타격 RPC는 약 85ms로 도착하고 랠리를 통과했다. **특정 타격 패킷 재전송이 단독 원인이라는 결론은 보류한다.** 로그를 켜면 실행 타이밍과 손실 난수 소비 경로도 달라질 수 있다.

서버 판정에는 과거 위치 복원이 없고 도착 시점의 높이를 사용한다. 지연에 의해 유효 타격이 놓치는 경로는 확인했지만, 이를 해결하려고 임의의 클라이언트 시각을 신뢰하거나 허용 높이를 낮추지는 않았다. 제한된 서버 이력 기반 지연 보상은 별도 설계·검증이 필요한 다음 구현 범위다.

## 실행 방법

```powershell
$taskRoot = 'D:/_Projects/FPS_Dell2g'
$taskPS = 'C:/Users/User/.cache/codex-runtimes/codex-primary-runtime/dependencies/native/powershell/pwsh.exe'
```

## 남은 과제와 최종 전달

이번 단계는 타격 지연 구간 계측·원인 범위 축소·실패 진단 개선을 완료했다. **75ms/3% 랠리 안정화 자체는 미완료**다. 다음 구현은 서버가 보관한 짧은 셔틀·플레이어 이력을 이용하는 제한적 지연 보상의 설계와 경계 검사다. 이미 확정된 득점·다른 랠리·중복 타격을 되돌리지 않도록 규칙을 먼저 정의해야 한다. 단순히 290ms를 모두 허용하거나 클라이언트 시간 값을 신뢰하는 방식으로 확장하지 않는다. 재전송의 정확한 인과관계는 실패 실행에서 RPC bunch/패킷을 직접 연결해야 확정할 수 있다.

기본 시계는 Legacy, RoundTrip은 후보로 유지한다. EOS/EQS·외부망 보류, 실제 사람 입력·PIE·별도 PC/LAN·MP4 미완료도 유지한다. 이번 변경은 화면 요소 변경이 없어 새 렌더링 캡처를 만들지 않았고, 과거 PNG를 이번 검사 증거로 재사용하지 않았다. 자동화 초기화의 EOS SDK 구성 연결 경고는 별도로 남으며 실제 EOS 로그인/방 검사를 수행한 것은 아니다. 기존 사용자 변경·OBS 소스는 보존했고 커밋은 하지 않았다.

최종 안내: 입력·GAS·서버 접촉 흐름 분석과 실패 자동 보고서를 추가했다. 실패에서 서버 활성화 전 약 290ms 지연을 확인하고 중간 랠리 종료 진단을 수정했다. 자동화 14개와 목표 조건의 패키지 조준·능력 검사는 통과했다. 스트레스 랠리는 여전히 실패가 있어 해결 완료로 표시하지 않았다. 전체 단계 및 테스트 문서를 20단계·54개 검사 기준으로 갱신했다.

최종 문서 검사에서 이 기록·체크리스트·전체 단계 요약의 로컬 링크 6/11/27개와 PowerShell 코드 블록 1/13/0개의 존재·구문을 확인했다. 체크 항목 54개는 중복이 없고 세 문서의 최신 패키지 해시가 실제 파일과 일치한다. 코드 블록 짝·문자 깨짐·줄 끝 공백 검사도 통과했다. 검사 종료 후 남아 있는 게임/UnrealEditor-Cmd 프로세스는 0개였다.
