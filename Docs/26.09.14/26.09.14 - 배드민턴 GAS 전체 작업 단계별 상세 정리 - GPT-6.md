## 2. 단계 01 — 초기 기획과 범위 확정

### 목표와 결정

UE5와 Gameplay Ability System을 사용해 샷 선택, 타격 타이밍, 상대 코트의 빈 공간 공략이 중심인 아케이드 배드민턴을 기획했다. Windows PC, 키보드·마우스, 1대1 단식, 코트 1개와 동일 능력치 캐릭터를 MVP로 정했다.

경기 흐름은 `입장 → 준비 → 서브 → 랠리 → 득점 → 다음 서브 → 결과 → 재경기`다. 초기 규칙은 랠리당 1점, 11점 선취 단판, 듀스 없음이다. 공식 경기 규칙 전체를 재현한 것으로 설명하지 않는다.

처음에는 LAN·직접 IP 검증과 이후 온라인 확장을 구분했으나, 사용자가 **첫 배포에 인터넷 방 생성·참가를 포함하고 EOS를 사용한다**고 결정했다. 따라서 EOS는 배포 완료 조건이다. 2대2, AI, 랭크, 전용 서버, 관전·리플레이, 성장·꾸미기는 후속 범위다.

### 산출물과 의미

- 10주 내외의 초기 개발 순서와 완료 기준을 작성했다. 이는 추정 일정이며 실제 10주 작업을 마쳤다는 뜻이 아니다.
- 서버 권한 판정, GAS 역할, 셔틀 동기화, 경기 상태 복제, 네트워크 검증 계획을 정의했다.
- 최초 작업 공간의 계획서와 실제 프로젝트 Docs의 계획서가 존재한다. 사용자 결정 및 이후 구현 상태는 프로젝트 Docs의 후속 기록과 함께 읽는다.

## 5. 단계 04 — GAS 기반과 기본 타격

### 구현 내용

- PlayerState에 AbilitySystemComponent와 Stamina/MaxStamina AttributeSet을 배치했다.
- Character를 ASC의 Avatar로 연결하고 소유·복제 시점에 초기화했다.
- 서버에서 능력을 부여하고 중복 부여를 방지했다.
- `UBadmintonClearAbility`에 Local Predicted 정책과 Gameplay Event 입력을 연결했다.
- 이벤트에 랠리 ID를 넣어 이전 랠리의 입력이 새 랠리에 적용되지 않도록 했다.
- `State.Swinging`과 회복 구간으로 연속 발동을 제한했다. 기본 클리어는 스태미나를 소비하지 않는다.

초기에는 서브와 리턴을 반복하는 연습 랠리였으며 점수는 없었다. 이후 단계 08~09에서 유료 샷과 경기 규칙으로 확장했다.

### 검증 결과와 한계

무지연 자동 입력에서 같은 랠리 ID로 10회 교대 타격했고 양쪽 샷 번호가 일치했다. 초기 타격은 발동 시점 판정으로 구현했으며, 최종 스켈레탈 애니메이션의 타격 구간과 정밀하게 맞춘 상태는 아니다. GAS 예측 적용이 셔틀 지연 보상 완료를 의미하지 않는다.

## 6. 단계 05 — 서버 셔틀 비행·복제·지연 검사

### 구현 내용

- 서버에서 중력과 선형 항력을 이용해 셔틀 비행을 계산했다.
- 최대 1/120초 간격 서브스텝과 이동 경로 Sweep으로 빠른 이동 중 충돌 누락을 줄였다.
- 위치·속도·서버 시간·랠리 ID·샷 시퀀스를 복제하고 클라이언트 화면 표시를 보정했다.
- 네트에 닿았다는 이유만으로 즉시 득점하지 않고 이후 낙하·통과 결과를 처리했다.
- 랠리 ID를 서버에서 검증해 늦은 요청을 거절했다.

현재 이동 로직의 구현 위치는 `ABadmintonShuttle`이다. 초기 계획의 `UShuttleMovementComponent`가 독립 클래스로 완성됐다고 표시하지 않는다.

### 실패와 수정 과정

첫 지연 테스트에서는 타격 10회가 5개 랠리에 흩어져 연속 랠리 기준에 실패했다. 자동 입력 검사 주기를 0.4초에서 0.05초로 보완하고 랠리 ID 전달을 적용한 후, 편도 50ms·송신 손실 1%에서 같은 랠리의 10회 교대 타격이 통과했다.

이 개선에는 테스트 입력 주기 수정이 포함되므로 사람의 입력 지연 문제가 모두 해결됐다고 해석하지 않는다.

### 검증

- 30/60/120fps 조건의 비행 계산에서 목표 도달 오차 1cm 미만을 검사했다.
- 내려오는 타점과 양쪽 코트 비행 대칭성을 검사했다.
- 초기 비행 자동화 2건은 통과했다. 엔진 초기화 중 별도 `Condition failed` 기록이 있었으며 ‘전체 로그 오류 없음’으로 표현하지 않았다.
- 제한된 과거 상태 재시뮬레이션 방식의 타격 지연 보상, 실측 RTT·보정 오차 통계는 완료 근거가 없다.

## 7. 단계 06 — EOS 포털·로고·로컬 설정 준비

### 포털 준비

사용자 화면과 기존 기록에서 조직 `KOREA`, 제품 `Lee`, Live Deployment, `BadmintonPeer2Peer` 정책과 `BadmintonGameClient` 생성을 확인했다. Epic Account Services 애플리케이션 `Badminton`의 권한과 연동된 클라이언트가 ‘구성됨’으로 표시된 것을 확인했다.

## 15. 단계 14 — 라켓 스윙·타격 피드백·셔틀 추적

### 구현 내용

- 기존 Cube/Cylinder 기본 도형으로 라켓 프레임·그립·스트링을 구성했다.
- 라켓 표시용 파트의 충돌·오버랩은 끄고 기존 서버 타격 판정을 사용했다.
- 입력 소유자는 즉시 예측 스윙을 표시하고 상대 화면에는 서버 승인 스윙 종류·랠리·시퀀스·시각·지속 시간을 복제했다.
- 소유자에게 같은 스윙 상태를 다시 복제하지 않아 예측과 서버 응답의 중복 재생을 방지했다.
- 서버가 타격 성공·헛스윙 결과를 소유자에게 보내 약 1.1초간 표시했다.
- 셔틀 위치에 마름모 추적 표시와 최근 6개 샘플의 짧은 잔상을 추가했다.

### 해결한 문제

스윙 상태가 새 랠리 GameState보다 먼저 도착하면 다음 Tick에 다시 처리하도록 했다. 과거 랠리·만료 스윙·중복 타격 결과가 현재 연출과 안내를 덮어쓰지 않도록 차단했다. 빌드에서는 테스트 변수 이름이 AController::Character를 가리는 오류를 수정했다.

### 검증

편도 50ms·손실 1%에서 같은 랠리 10회 교대 타격 후 양쪽 각각 `localSwings=5`, `remoteSwings=5`, `contacts=5`를 확인했다. 기존 비용·스태미나 부족·연속 및 오래된 입력·대시 검사도 통과했다. 드롭·스매시 헛스윙 결과 전달은 로그로 확인했다.

에디터·게임 빌드와 패키징이 성공했고 실제 패키지에서도 같은 연출 횟수를 확인했다. 1280×720 렌더링에서 라켓, 스윙 중 RECOVERING, CLEAR / CONNECTED와 셔틀 추적 표시를 확인했다.

최종 캐릭터 애니메이션·손 위치·그립 정렬·사운드는 남아 있다. 원격 스윙이 유효 지속 시간보다 늦게 도착하면 연출이 생략될 수 있다. 셔틀 추적 표시는 착지 예측이나 추가 타격 판정이 아니다.

## 16. 단계 15 — 마우스 샷 조준과 서버 목표 검증

### 구현 내용

기존 샷이 정해진 중앙 지점으로만 향하던 상태를 개선했다. 마우스 좌우·상하 입력으로 정규화한 두 축 조준값을 누적하고 가운데 버튼과 새 랠리 시작 시 중앙으로 초기화한다. 캐릭터 이동과 별개로 방향·깊이를 선택한다.

조준값을 GAS 이벤트의 TargetData로 보내며 서버는 자료형·개수·LiteralTransform 위치 형식·유한값·허용 범위와 진영을 검증한다. 클라이언트가 보낸 임의의 코트 좌표를 그대로 사용하지 않고 서버의 ShotData로 목표를 계산한다. 비정상 요청은 비용 차감 전에 거절한다.

- 일반 조준 폭 기본값: 180cm.
- 깊이 조절 기본값: 80cm.
- 서브 좌우 조준: 대각 서비스 구역 안으로 제한.
- 중앙 조준 `(0,0)`: 기존 샷 목표 유지.
- 화면 AIM 표시: 방향·깊이 안내. 실제 착지 예상점이 아니라 샷 프로필의 TargetHeight를 지나는 기준 목표다.
