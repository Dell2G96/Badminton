## 사용자 질문 및 결정

- 질문: 첫 배포 목표가 LAN·직접 IP 시연인지 인터넷 방 생성·참가까지 포함하는지 확인 요청.
- 사용자 결정: 첫 배포에 인터넷 방 생성·참가를 포함하며 온라인 서비스는 Epic Online Services(EOS)를 사용한다.
- 질문: EOS 제품과 Sandbox/Deployment 생성 여부를 확인했다. 사용자 답변: 아직 없으며 생성·설정 안내가 필요하다. [EOS 준비 안내](<26.09.14 - EOS 제품 생성 및 연결 준비 안내 - GPT-6.md>)를 작성했다.
- 질문: 기존 OBSRecording 플러그인 오류로 전체 빌드가 막혀 임시 비활성화 또는 함께 수정을 요청했다.
- 사용자 결정: OBS 플러그인을 프로젝트에서 임시 비활성화한다. 소스는 보존하고 `.uproject`에서 `Enabled=false`로 지정했다.
- EOS는 온라인 연동 단계에서 프로젝트 설정·로그인·세션·P2P 접속과 외부망 검증을 추가한다. 공식 참조: [Online Subsystem EOS](https://dev.epicgames.com/documentation/unreal-engine/online-subsystem-eos-plugin-in-unreal-engine). 현재 기본 IP 접속 검증을 EOS 인터넷 플레이 완료로 표시하지 않는다.

## 1단계 구현 방침

- 기존 FPS 클래스·맵과 기존 배드민턴 시연 에셋을 보존한다. 새 배드민턴 클래스로 분리하며 모듈명 FPS_Dell2g를 유지한다.
- 신규 테스트 맵과 코드 기반 코트로 기본 동작을 검증한다. 기존 캐릭터·애니메이션은 호환성 확인 후 사용한다.
- 한 코트에 두 명까지 배치하고 서버가 코트 편과 준비 상태를 관리한다. 양쪽에서 W가 네트 방향이 되도록 입력·카메라를 구성한다.
- 모든 단계에서 구현 상태와 검증 상태를 별도로 기록하며, 미실행 검증은 통과로 표시하지 않는다.

## 검증

진행 중. 현재까지 프로젝트 설정, 소스 구조, 에셋 목록, 설치 엔진 버전과 Git 상태를 확인했다.

- 기존 빌드: 사용자 전역 UnrealBuildTool 로그와 UBA 폴더 접근 권한 문제 발생. 명령 인수로 프로젝트 내부 로그 경로와 `-NoUBA`를 사용하여 전역 폴더 변경 없이 해결했다.
- 기존 소스 오류: GameplayTags 링크 의존성 누락, OBSRecording 자체 include 및 불완전 타입 소멸 오류 확인. GameplayTags는 GAS 기반 구성과 함께 추가했고 OBS는 사용자 결정에 따라 임시 비활성화했다.
- 1단계: 전용 게임 클래스, 코트와 경계, 양쪽 카메라·입력, 2인 제한·준비 상태를 구현하고 빌드 검증 중이다. 2단계의 ASC/AttributeSet 연결도 기본 구조에 포함했다. 캐릭터 외형은 판정 검증을 위한 임시 원통이며 기존 에셋은 수정하지 않았다.

추가 진행 답변: 첫 배포 범위에 인터넷 방 생성·참가를 포함하겠습니다. 기존 배드민턴 모델과 동작 에셋도 확인했습니다. 현재 빌드는 소스 컴파일 전에 UnrealBuildTool의 사용자 폴더 접근 권한에서 멈춰, 빌드 환경부터 정리하고 있습니다.

추가 진행 답변: 온라인 서비스는 EOS로 확정했습니다. 빌드 환경 문제를 넘긴 뒤에는 기존 GameplayTags 의존성 누락과 OBS 녹화 플러그인의 컴파일 오류가 확인됐습니다. GameplayTags는 GAS 기반 구성과 함께 보완하고, OBS 처리 방식은 확인받는 동안 배드민턴 전용 코드 작업을 진행하겠습니다.

추가 진행 답변: 요청하신 대로 OBS 플러그인을 임시 비활성화하고, GAS 의존성과 배드민턴 전용 클래스들을 추가하고 있습니다. 우선 서버가 두 플레이어를 코트 양쪽에 배치하고, 각자의 화면에서 W 키로 네트 쪽으로 이동하는 동작을 검증하겠습니다.

추가 진행 답변: 두 개의 독립 프로세스에서 1단계 네트워크 검증이 통과했습니다. 서버와 참가자 모두 이동 복제, 코트 경계, 서로 다른 진영, 준비 상태, ASC 연결이 확인됐습니다. 다음으로 기본 타격 능력과 서버 셔틀콕 비행을 연결하겠습니다.

추가 진행 답변: 기본 타격 검증도 통과했습니다. 한 랠리에서 양쪽이 번갈아 10회 타격했고, 두 프로세스 모두 같은 랠리 ID와 샷 번호를 확인했습니다. 이어서 지연·패킷 손실 조건을 검사하고, 실행 방법과 EOS 설정 안내를 정리하겠습니다.

추가 진행 답변: 입력 주기를 보완한 재검증에서 편도 50ms 지연과 송신 패킷 손실 1% 조건에서도 한 랠리 10회 교대 타격이 통과했습니다. 프레임 속도에 따른 비행 계산과 코트 양쪽의 대칭성 테스트도 통과했습니다. 현재 결과는 자동 입력 기반이며, 실제 조작감과 화면상 보정 품질은 별도로 확인해야 합니다.

추가 진행 답변: 정원 초과 검사에서도 세 번째 참가자가 거절되는 것을 확인했습니다. 기본 맵과 실행 스크립트, 검증 기록을 정리했고, 현재는 실제 렌더링 화면을 확인하기 위한 첫 셰이더 컴파일이 진행 중입니다.

## 구현 상세

- 새 기본 맵: `Content/Badminton/Maps/L_Badminton_Prototype.umap`. UE Python commandlet으로 생성했고 기존 맵은 보존했다.
- 코트: 바닥, 라인, 네트와 플레이어 경계. 첫 캐릭터는 원통, 셔틀콕은 구로 표시한다.
- 입장: 서버가 두 진영을 할당하고 세 번째 접속을 `BadmintonRoomFull`로 거절한다.
- 입력: Enhanced Input WASD·Enter·좌클릭. 카메라와 이동 기준은 자신의 코트 뒤에서 상대를 보는 방향이다.
- GAS: PlayerState의 ASC·Stamina/MaxStamina, Character의 Owner/Avatar 초기화, 서버에서 중복 없이 기본 능력 부여. 기본 타격은 Stamina를 소비하지 않는다.
- 능력: `UBadmintonClearAbility`는 Local Predicted와 Gameplay Event를 사용한다. 이벤트에 랠리 ID를 실어 서버가 현재 랠리와 일치하는지 확인한다. `State.Swinging` 태그와 0.35초 회복 구간으로 중복 발동을 제한한다. 초기 샷은 발동 시점에 판정하며 애니메이션 구간 판정·조준은 후속이다.
- 셔틀콕: 서버에서 중력과 선형 항력 모델을 계산하고 최대 1/120초 간격 Sweep으로 이동한다. 네트 접촉은 즉시 득점 판정하지 않고 낙하를 계속한다. 위치·속도·서버 시간·랠리 ID·샷 번호를 복제하고 클라이언트 표시를 보정한다.
- 랠리: 현재는 기본 서브와 리턴, 낙하 시 연습 종료·다음 서브 준비만 구현했다. 공식 점수, 아웃 판정, 서비스 구역, 경기 종료는 아직 미구현이다.
- 셔틀 이동은 현재 `ABadmintonShuttle` 안에 있으며, 샷 종류가 늘어나는 단계에서 전용 이동 컴포넌트와 ShotDataAsset으로 분리할 예정이다.
- EOS: 사용자가 서비스와 첫 배포 범위를 확정했다. 제품이 아직 없으므로 인증·세션 설정이나 인터넷 플레이를 완료했다고 표시하지 않는다.

지연 테스트는 양쪽 송신에 PktLag=50ms, PktLoss=1%를 적용했고 엔진 로그에서 실제 설정 적용을 확인했다. 추가 RTT 약 100ms에 해당하는 설정이며, 관측 RTT 통계 자체는 아직 계측하지 않았다. 랠리 테스트는 자동 입력을 사용하므로 사람이 느끼는 판정 품질이나 실전 인터넷 품질을 보장하는 결과가 아니다.

비행 자동화는 30/60/120fps에서 목표 도달 오차 1cm 미만, 내려오는 타점과 양쪽 비행 대칭성을 검사했다. 지정 테스트가 실행되기 전 엔진 초기화 로그에 `Condition failed` 4건이 별도로 있었고 원인은 아직 분류하지 않았다. 이를 지정한 두 테스트의 실패나 전체 엔진 오류 없음으로 오인하지 않는다.
